## 1. רקע ובעיה עסקית

הארכיטקטורה הנוכחית מציבה את אייל כפרסונה ב-`CLAUDE.md`. זה עובד, אבל יוצר שתי בעיות:

1. **חוסר הפרדה בין שכבת התשתית של Claude לבין שכבת הלוגיקה הניהולית.** CLAUDE.md אמור להגדיר הקשר טכני, לא לכלול פרסונה ארוכה.
2. **קושי לקרוא לאייל באופן מודולרי.** היום אייל = השיחה. אם נרצה לבדוק אותו בנפרד, לכתוב לו בדיקות, או לעדכן אותו בלי לעדכן את CLAUDE.md — אי אפשר.

**הפתרון:** אייל הופך לסוכן נפרד עם `agent.md` ייעודי. CLAUDE.md יוגדר ש"בכל פנייה — קרא לסוכן `eyal`".

## 2. מטרות

1. ליצור סוכן `eyal` עצמאי שמרכז את כל הלוגיקה הניהולית של המערכת.
2. לאפשר ל-CLAUDE.md (שיעודכן בנפרד על ידי המפתח) להפעיל את אייל אוטומטית בכל פנייה.
3. לתת לאייל יכולת **להסיק מהקשר** לאיזה סוכן-משנה לפנות, להפעיל מספר סוכנים **במקביל** כשאפשר, ולסנתז את התוצאות לסיכום ניהולי אחד.
4. לאכוף **gate אישור להפצה חיצונית** לפני שברק מפיק PDF להפצה.
5. לשמור על שקיפות מלאה — כל החלטה של אייל ניתנת לקריאה אחורה ומקושרת לתוצרים.

### 2.1 מחוץ להיקף

- אייל לא כותב תוכן בעצמו (לא Excel, לא טקסט דוחות, לא שקפים). הוא **תמיד מאצל** ל-גל/אירית/בר/ברק.
- אייל לא מבצע פעולות פיננסיות (לא מאשר תקציבים, לא שולח תשלומים).
- אייל לא מקבל החלטות אסטרטגיות אוטונומיות (מכירת רכבים, פיטורי נהגים). הוא ממליץ — גלעד מאשר.

## 3. User Stories

1. **כגלעד**, אני שולח לאייל בקשה חופשית בעברית, ומקבל תוצרים מוכנים בלי לחשוב באיזה סוכן להשתמש.
2. **כגלעד**, כשאני מבקש דוח שנתי שלם, אייל מפעיל את גל, ואז בר ואירית במקביל, ומקצר את זמן ההמתנה.
3. **כגלעד**, כשאני מבקש PDF להפצה חיצונית, אייל עוצר ומבקש אישור לפני שברק מפיק את הקובץ.
4. **כגלעד**, בסיום משימה אני מקבל מאייל **סיכום ניהולי** (לא רשימת קבצים יבשה) שאומר מה החריגים, מה ההמלצה הניהולית, ואיפה הקבצים.

## 4. דרישות פונקציונליות

### 4.1 הפעלה אוטומטית מ-CLAUDE.md

CLAUDE.md (יוצר בנפרד על ידי המפתח) יכלול הוראה ש**כל פנייה של גלעד מועברת לסוכן `eyal`**, פרט לפניות טכניות-תפעוליות (לדוגמה debug של תשתית, הרצת `/git push`).

- מבחינת אייל — הוא תמיד מקבל את הבקשה דרך CLAUDE.md ולא ישירות.
- מבחינת ה-`description` של אייל ב-frontmatter — היא תהיה רחבה מספיק כדי שמערכת ה-routing של Claude Code תזהה אותו ב-default לכל בקשה רלוונטית לצי.

### 4.2 לוגיקת הקצאה (Intent-Based Delegation)

אייל מבין את כוונת הבקשה מההקשר ומחליט אילו סוכנים להפעיל. אינדיקטורים:

| אינדיקטור בבקשה | סוכן(ים) |
|------------------|-----------|
| "ניתוח", "KPI", "פילוח", "נתונים", "צריכת דלק" | **גל** (תמיד ראשון) |
| "מצגת", "להציג להנהלה", "סקירה" | **אירית** |
| "דוח", "סיכום שנתי", "מסמך" | **בר** |
| "PDF", "להפיץ", "סגור", "ארכוב" | **ברק** |
| "דוח שנתי שלם", "תיק רבעוני להנהלה" | **גל → (אירית+בר במקביל) → ברק** |

**חוק ברזל:** גל תמיד ראשון בכל ניתוח חדש. אסור להפעיל סוכן אחר על נתונים שלא עברו טיוב.

### 4.3 ריצה מקבילה

כשמשימה דורשת מספר תוצרים על אותו ניתוח (Excel + Word + PowerPoint), אייל מפעיל את אירית, בר וברק **במקביל** (single message, multiple Agent calls). מקרים שדורשים ריצה סדרתית:

- כל מקרה שבו ברק מעורב — תמיד אחרון.
- כשתוצר אחד תלוי בתוצר אחר (לדוגמה — בר רוצה לצטט מספרים שאירית ייצרה).

### 4.4 סינתזה ניהולית (Output Synthesis)

לאחר שכל הסוכנים סיימו, אייל מחזיר לגלעד **תשובה אחת** במבנה:

```
📊 סיכום מנהלים
[2-4 שורות פרוזה — מה היה הניתוח, מה הממצא העיקרי, רמת חתך]

⚠️ חריגים מהותיים
• [חריג 1 + נתון]
• [חריג 2 + נתון]

💡 המלצות פעולה (3-5)
1. [פעולה + הצדקה כספית/בטיחותית]
2. ...

📁 קבצי תוצר
• Excel:       output/<path>.xlsx
• PowerPoint:  output/<path>.pptx
• Word:        output/<path>.docx
• PDF:         output/<path>.pdf  (טרם הופק — דורש אישור הפצה)

🔄 המשך אפשרי
[רצף פעולות שגלעד יכול לבקש: "תפיק PDF פנימי", "הוסף חתך לסניף חיפה" וכו']
```

### 4.5 Approval Gate להפצה חיצונית

לפני שברק מפיק PDF המסומן `ייעוד=חיצוני`, אייל **חייב** לעצור ולשאול את גלעד:

> "ה-PDF מיועד להפצה חיצונית. האם אתה מאשר?
>  📄 שם הקובץ: ...
>  🎯 רמת חתך: ...
>  📅 גרסה: v1.0
>  ⚠️ בדוק שאין נתוני נהגים אישיים שלא מותר להפיץ."

רק אישור מפורש מאפשר לברק להמשיך.

### 4.6 הצפת חריגים ופערי נתונים

אייל מציף לגלעד ב-3 מצבים:
1. **חוסר נתונים מהותי** — מעל 10% מהשדות הקריטיים חסרים.
2. **חריגה כספית מהותית** — קפיצה > 50% בעלות בין תקופות, או רכב/סניף עם TCO > פי 2 מהממוצע.
3. **התנגשות הרשאות** — אם הבקשה דורשת נתונים שגלעד לא מורשה לראות.

### 6.2 גוף ה-agent.md — מבנה מומלץ

1. **זהות** — מי אני, למי אני מדווח, מי מדווח לי.
2. **עקרונות עבודה** — שפה, סודיות, שקיפות, חוק "גל תמיד ראשון".
3. **תהליך עבודה סטנדרטי** — 6 שלבים מקבלת בקשה ועד החזרת סיכום.
4. **טבלת אינדיקטורים לסוכנים** — מתי להפעיל מי (לפי §4.2).
5. **טמפלייט סיכום ניהולי** — בדיוק לפי §4.4.
6. **Approval Gate** — נוסח שאלה מדויק לפני הפצה חיצונית (§4.5).
7. **פרוטוקול הצפת חריגים** — 3 המצבים מ-§4.6.
8. **קריטריוני קבלה** — בקרת איכות לפני החזרה לגלעד.
9. **הפניות** — לקבצי הסוכנים (gal/irit/bar/barak) וסקילים רלוונטיים.

### 6.3 כלים נדרשים (tools)

| כלי | שימוש |
|------|--------|
| `Read` | קריאת קבצי קלט, תוצרי סוכני-משנה לסקירה |
| `Write`, `Edit` | יצירת/עדכון `vault/Meeting Notes/` עם סיכומי משימות |
| `Bash` | בדיקות קלות (לוודא שקובץ נוצר, רץ דרך `ls`/`stat`) |
| `Glob`, `Grep` | חיפוש קבצי קלט ב-`input/` ותוצרים ב-`output/` |
| `Skill` | הפעלת `obsidian-vault-workflow` בתחילת/סוף משימה |
| **`Agent`** | **קריטי** — להפעלת גל/אירית/בר/ברק |

### 6.4 מודל

`sonnet` — מספיק חכם לסינתזה, מהיר מספיק כדי לא להאריך latency. אם נגלה שצריך יותר עומק לחריגים — נשדרג ל-`opus`.

## 8. סיכונים ותלויות

- **CLAUDE.md חיצוני:** ה-PRD מניח ש-CLAUDE.md ייכתב על ידי המפתח של גלעד וייגרום ל-Claude לקרוא לסוכן `eyal`. אם המפתח לא יממש את ה-routing הזה — אייל יישאר סוכן "רדום" שצריך לקרוא לו ידנית.
- **תמיכת Agent tool:** Claude Code חייב לתת לסוכן הרשאת קריאה ל-Agent tool. נכון להיום — כן, אבל כדאי לאמת בסשן ראשון.
- **התנגשות בין auto-routing של Claude Code לבין CLAUDE.md:** אם מנגנון ה-`description` של אייל יתפוס *לפני* ש-CLAUDE.md מספיק להקצות — זה תקין; אם הסדר הפוך — צריך לוודא שהתוצאה זהה.
- **PRD תלוי בסקילים קיימים:** אייל מסתמך על כך שגל/אירית/בר/ברק קיימים ועובדים. שינוי מהותי בסקיל של אחד מהם — דורש סקירה של ה-Approval Gate או של טמפלייט הסיכום.
